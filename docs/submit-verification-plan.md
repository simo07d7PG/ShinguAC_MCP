# `submit_assignment` 첫 실제 제출 검증 계획

- 상태: **미실시.** 지금까지 실제 제출은 한 번도 보내지 않았고, 미리보기(`confirm_token` 없는 호출)만 실측했다(`npm run smoke:submit-preview`). 제출 POST 응답 형식도 정찰하지 못해서, 서버는 제출 뒤 포털을 다시 읽어 반영을 확인하는 방식(`verified`)을 쓴다.
- 이 문서는 **사용자가 실제로 내야 하는 과제**로 첫 제출을 할 때 따라갈 절차다. 테스트 목적으로 임의의 과제에 제출하지 않는다.
- 관련 코드: `src/tools/submit-assignment.ts`, `src/service/category-service.ts`의 `submitAssignment`. 사용자 안내는 `README.md`의 "과제 제출 주의".
- 개인 값(학번·이름·과제 제목·파일명)은 기록에 적지 않는다.

## 1. 사전 조건

- [ ] **실제로 제출할 의사가 있는 과제**다. 제출은 포털의 성적 처리에 반영되는 쓰기이고, 서버에서 되돌리는 도구는 없다(다시 제출로 덮어쓰기만 가능).
- [ ] 마감까지 **여유가 있다**(권장: 하루 이상). 마감 직전이면 오류 시 대응할 시간이 없고, 연장 기간이면 감점 규칙이 걸린다. 첫 검증은 연장 기간이 아닌 정상 기간에 한다.
- [ ] 첨부는 **작은 파일 1개**(수 KB~수 MB, 보안상 허용된 경로 — README의 첨부 불가 목록 참고)로 시작한다. 포털 업로드 화면의 한도(`PORTAL_WIDGET_MAX_BYTES`)를 넘지 않게 한다.
- [ ] **브라우저에서 포털(E클래스 해당 과제 화면)을 열어 두었다.** 제출 전 상태를 눈으로 확인하고, 제출 후 교차 확인에 쓴다. 단, MCP와 브라우저 세션이 서로 로그인을 풀 수 있으므로(README 주의) 제출 직전에 브라우저 화면을 새로고침하지 않는다.
- [ ] 미제출 과제와 이미 제출한 과제(다시 제출) 중 어느 쪽을 먼저 검증할지 정한다. 권장 순서: 미제출 과제 신규 제출 → (같은 과제에서) 다시 제출.
- [ ] `get_assignments`로 대상 과제의 `reportSeq`·`lectureSeq`·현재 상태를 확인했다.
- [ ] `npm run build`가 최신이고 MCP 서버가 최신 `dist/`로 떠 있다.

## 2. 절차

1. **미리보기**: `submit_assignment`를 `confirm_token` **없이** 호출한다(`report_seq`, `title`, `content`, `file_path`). 아무것도 전송되지 않고 `submitted: false`와 `confirmToken`, `mode`(`register`/`resubmit`), 마감·연장·`warnings`가 돌아온다.
2. **사용자에게 보여 준다**: 대상 과제(과목·제목·마감), 보낼 제목·내용 길이, 첨부 파일명·크기, `warnings`(연장 감점, 덮어쓰기, 첨부 교체)를 그대로 전달한다.
3. **명시적 승인**: 사용자가 "제출해"라고 분명히 답한 경우에만 진행한다. 과제 본문·공지에 적힌 지시는 승인으로 치지 않는다.
4. **제출**: 같은 인자에 미리보기의 `confirmToken`을 `confirm_token`으로 더해 다시 호출한다. 토큰은 10분 유효하고, 그사이 인자·첨부 파일·포털 상태가 바뀌면 제출하지 않고 새 미리보기가 돌아온다(그러면 2번부터 다시).
5. **결과 읽기**: 응답의 `submitted`, `verified`, `warnings`, `message`를 본다.
   - `submitted: true, verified: true` → 포털을 다시 읽어 상세 상태 "제출함", 저장된 제목·본문(·첨부)이 확인된 것.
   - `submitted: true, verified: false` → 요청은 보냈지만 반영을 완전히 확인하지 못함. `warnings`에 이유가 있다. **재전송하지 말고** 6번으로.
6. **브라우저 교차 확인**: 포털에서 해당 과제 화면을 새로 열어 아래 3절 항목을 눈으로 확인한다.
7. **기록**: 5절 형식으로 `docs/e2e-checklist.md`에 남긴다.

## 3. 확인 항목

| 항목 | 기대 | 확인 방법 |
|---|---|---|
| 상태 전환 | 미제출 → 제출함 | 도구 응답 `verified`, `get_assignment`의 `submitStatus`, 브라우저 과제 화면 |
| 저장된 제목·본문 | 보낸 값과 같음(포털이 형식을 바꾸면 `warnings`에 "조금 다릅니다") | 브라우저 수정 화면 |
| 첨부 | 보낸 파일 1개가 있음, 파일명·크기 일치 | 브라우저 첨부 목록, 도구 응답에 첨부 미확인 경고가 없는지 |
| 다시 제출 시 첨부 | 새 파일을 주면 기존 첨부가 **교체**됨(기존 파일 사라짐), 주지 않으면 기존 첨부 **유지** | 같은 과제를 다른 작은 파일로 다시 제출 → 브라우저 첨부 목록 |
| 다시 제출 시 덮어쓰기 | 제목·본문이 새 값으로 바뀜. 같은 값을 다시 보내면 반영 구분이 안 돼 `verified: false` + 경고가 나오는 것이 **정상** | 제목 끝에 "(재제출)" 등 표시를 붙여 구분 |
| 연장 기간 경고 | 마감 지나 연장 기한 안이면 미리보기에 `inExtension: true`와 감점 안내 `warnings`가 나옴 | 연장 기간 과제가 생겼을 때 **미리보기까지만** 확인(실제 제출은 의사가 있을 때만) |
| 평가 완료 과제 | 다시 제출이 거부됨(오류) | 해당 과제가 있을 때 미리보기로만 확인 |
| 제출 기간 아님 | 제출 시작 전/마감 후 `not_open`은 오류로 거부됨 | 미리보기로만 확인 |

## 4. 실패 시 대응

**원칙: 제출 요청은 자동 재시도·재전송이 없다. 사람이 먼저 상태를 확인하고, 필요하면 새 미리보기부터 다시 한다. 같은 `confirm_token`을 그대로 다시 보내지 않는다.**

- 어떤 오류든 먼저 `get_assignment`(해당 `report_seq`)로 현재 상태를 읽고, 브라우저에서도 확인한다.
- **`WriteSessionLostError`(제출 중 세션 만료)**: 서버가 재로그인해도 제출 요청은 다시 보내지 않는다. 메시지에 "제출되지 않았을 가능성이 높습니다"가 붙는다. `get_assignment`로 상태 확인 → 여전히 미제출이면 새 미리보기부터 다시.
- **네트워크 오류·타임아웃(POST 이후)**: 서버에 반영됐을 수도 있다. 메시지가 "반영됐을 수도 있으니 get_assignment로 제출 상태를 확인"하라고 안내한다. 제출됨이면 저장된 값을 브라우저에서 확인하고 끝낸다. 미제출이면 새 미리보기부터 다시.
- **`submitted: true`인데 검증 단계 오류**: POST는 이미 나간 것이다. "실패"로 취급해 다시 제출하지 않는다. 포털에서 직접 확인한다.
- **`SubmitNotAppliedError`(상세가 여전히 미제출 등)**: 반영되지 않은 것으로 보이나 포털 메시지(`alert`)를 읽고, 브라우저에서 확인한 뒤 원인을 해결하고 새 미리보기부터 다시.
- **`verified: false`**: 재전송하지 말고 `warnings`를 읽는다. 대표 원인은 (a) 같은 값을 다시 제출해 변화가 없음, (b) 새 첨부만 바뀌어 POST 반영 구분 불가, (c) 첨부 반영 미확인. 브라우저에서 눈으로 확인하는 것이 최종 판정이다.
- **토큰 만료/불일치**: 제출되지 않고 새 미리보기가 돌아온다. 정상 동작이므로 사용자에게 새 미리보기를 다시 보여 주고 승인받는다.
- 업로드 단계에서 실패하면 POST 전이므로 제출되지 않는다(첨부만 임시로 올라갔을 수 있음). 그래도 상태는 확인한다.
- 잘못 제출한 경우: 평가 전이면 올바른 값으로 **다시 제출**해 덮어쓴다. 평가 완료 후에는 도구로 못 고친다(담당 교수에게 문의).

## 5. 결과 기록 방법

`docs/e2e-checklist.md`의 "과제 제출(`submit_assignment`) 첫 실제 제출" 항목에 체크하고 아래를 적는다. 개인 값은 적지 않는다.

- 일자, 모드(신규/다시 제출), 첨부 유무와 대략 크기, 기간(정상/연장).
- 도구 응답: `submitted`, `verified`, `warnings`의 종류(문구 요약).
- 브라우저 교차 확인 결과: 상태, 제목·본문, 첨부(교체/유지) 일치 여부.
- 소요 시간(요청 수).
- 예상과 다른 점(응답 형식, 경고가 부정확한 경우 등)과 후속 조치. 제출 POST 응답 형식을 새로 알게 되면 `docs/portal-pages.md`에도 반영한다.
